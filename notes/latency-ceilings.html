Can you prove a latency ceiling?

Scott Nelson, Data Engineer

Honesty

This is a synthesis of published results. It does not prove that any Mobilint/NPU run finishes under 12 or 14 ms.

The answer

Yes, but only inside a model that states how work arrives and how fast the machine serves it.

If the model does not state both, a formula can still print a number. That number is not a proof that the machine finishes by then.

A deterministic ceiling

Network calculus, in Le Boudec & Thiran, is one such model. An arrival curve $\alpha$ bounds how much work can show up. A service curve $\beta$ bounds how fast the machine serves it. Delay at time $t$ is at most the horizontal deviation of those two curves:

$$d(t) \le h(\alpha,\beta)$$

The horizontal deviation is the smallest $\tau$ such that $\alpha(s) \le \beta(s+\tau)$:

$$h(\alpha,\beta) = \inf\{\tau \ge 0 : \alpha(s) \le \beta(s+\tau)\ \text{for all}\ s \ge 0\}$$

The bound is tight for a good arrival curve $\alpha$ and a wide-sense increasing service curve $\beta$ with $\beta(0)=0$. A greedy source achieves it.

Static-priority preemptive scheduling has its own ceiling, from the response-time analysis of Audsley, Burns, Richardson, Tindell, and Wellings. Let $r_i$ be the response time of task $i$, $C_i$ its execution time, $B_i$ its blocking, $T_j$ the period of a higher-priority task $j$, and $hp(i)$ those higher-priority tasks. The response time solves

$$r_i = C_i + B_i + \sum_{j \in hp(i)} \left\lceil \frac{r_i}{T_j} \right\rceil C_j$$

The deadline holds if and only if $r_i \le D_i$, where $D_i$ is the deadline of task $i$.

That kind of bound is machine-checkable. Maida, Bozhko & Brandenburg, at ECRTS 2022, attach a Prosa certificate in Coq to a computed response-time bound, so a checker can confirm the bound rather than trust the tool that printed it.

Probability instead of a ceiling

Give up a number the delay is forbidden to cross, and the question becomes a tail. For an M/M/1 queue, with utilization $\rho$ and service rate $\mu$, the waiting time $W$ satisfies

$$P(W > t) = \rho \exp(-\mu(1-\rho)t)$$

For general queues the tails are exponential from both sides: an upper bound and a lower bound of exponential form. That is the conclusion Kelly draws, citing Kingman and Ross.

Stochastic network calculus moves the same idea onto a network. The result is a bound on the probability that delay exceeds a level, not a level it cannot exceed.

A probabilistic worst-case execution time from extreme-value theory — the pWCET results of Cazorla et al. — is valid only for the conditions that were sampled.

What delay is made of

End-to-end delay is several different times added together:

  • Processing, the work done at a node.
  • Queueing, the wait behind other work.
  • Transmission, $L/R$, packet length over link rate. It does not depend on distance.
  • Propagation, $d/s$, distance over speed. The speed $s$ is about $2\times 10^{8}$ to $3\times 10^{8}$ m/s.

When queueing is negligible, the sum scales with the hop count. TCP adds a round trip before data. RFC 7413 specifies TCP Fast Open, the mechanism concerned with data on that opening exchange.

No single source writes one equation that contains all of these terms. In Kurose & Ross, the end-to-end delay expression drops queueing.

When the exact worst case is computable

Bouillard & Thierry separate three cases.

  • A tandem of servers reduces to one linear program, of polynomial size.
  • In a general feed-forward network, the exact worst-case delay at one server is NP-hard.
  • Cyclic networks are open.

A bound is a different object from the exact worst case. The bound can be larger than the exact worst case, so passing a bound is not the same fact as knowing the worst case.

An NPU latency target

A FLOP count or a parameter count is not an arrival curve, and it is not a service curve. To write $\alpha$ and $\beta$ for an NPU you need a service model: bytes moved, memory bandwidth, MAC throughput, launch and runtime overhead, and interference. Without that model, the expression you can actually defend is a lower bound, activation bytes divided by bandwidth. A lower bound does not certify a ceiling.

The measurements in hand are these. A model with 0.12M parameters measured 14.0 ms. A fastest run measured 12.2 ms. A model with 78 times more parameters cost about 29 times the time, so a small model is paying a fixed floor. A formula that ignores that floor cannot certify the bucket.

None of those figures is a proof that a run finishes under 12 or 14 ms. They are measurements of particular runs, not a service curve.
